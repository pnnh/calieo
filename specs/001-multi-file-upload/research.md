# Phase 0 研究：批量文件上传与同目录自动重命名

**功能**: [spec.md](./spec.md) | **日期**: 2026-08-02

本功能基于已有的单文件上传实现（`src/app/[lang]/console/upload/route.ts` + `src/components/FileUploadForm.tsx`），技术栈与部署环境均无变化，因此本阶段无需引入新语言/框架/基础设施的调研，仅需就以下几项实现方式做出决策。

## 决策 1：批量请求的处理方式

- **决策**: 由客户端将整批文件放入同一个 `multipart/form-data` 请求中（`file` 字段重复出现多次），服务端一次性接收并使用 `formData.getAll("file")` 逐一顺序处理，而不是客户端为每个文件分别发起独立的上传请求。
- **理由**: 只有在服务端拿到完整批次后，才能在处理任何文件之前对数量（≤20）与总大小（≤300 MB）做一次性的 all-or-nothing 前置校验；单一请求也让"同批次内重名文件"的处理顺序确定、可预测，避免并发请求下的竞态问题。
- **考虑过的替代方案**: 客户端为每个文件单独发起请求（并发或串行）——难以在提交前一次性校验批次总大小，且并发场景下同批次重名文件的处理顺序不确定，与 FR-004/FR-007 的确定性要求冲突，故不采用。

## 决策 2：随机文件名后缀的生成方式

- **决策**: 使用运行时内置的 `crypto.randomUUID()`，截取其中一段（如去掉连字符后取前 8 位十六进制字符）作为后缀，格式为 `{原始文件名（不含扩展名）}-{随机后缀}{扩展名}`；若生成结果仍与已存在文件名冲突（理论概率极低），重新生成后缀直至不冲突。
- **理由**: `crypto.randomUUID()` 在 Node.js（本地开发）与 Cloudflare Workers（生产运行时）中均原生可用，无需引入新的 npm 依赖，冲突概率可忽略不计。
- **考虑过的替代方案**:
  - 复用现有 `uuidv7` + `bs58`（`src/db/schema.ts` 中的 `createId`）生成完整短 ID 作为后缀——生成的后缀过长，影响文件名可读性，故不采用。
  - 使用时间戳作为后缀——同一批次中的多个同名文件可能在同一毫秒内处理，时间戳精度不足以保证唯一性，故不采用。

## 决策 3：批次级限制与单文件级失败的处理边界

- **决策**: 将"批次文件数量 ≤20""批次总大小 ≤300 MB"作为**批次级前置校验**：在服务端开始处理任何文件之前完成校验，一旦超限则整体拒绝请求（返回 4xx，不创建任何文件记录、不写入任何存储）。将"单文件大小 ≤20 MB""存储写入失败""文件名冲突处理"等作为**单文件级处理**，按 continue-on-error 策略逐个执行，个别文件失败不影响批次中其余文件。
- **理由**: 与规格中 FR-002 / FR-010（"必须在提交前明确提示，且不得发起上传请求"）以及 FR-005（"批次中任一文件…失败时…只跳过该文件并继续处理批次中的其余文件"）的措辞保持严格一致，两者语义边界清晰，避免实现时混淆"批次级拒绝"与"单文件级跳过"。
- **考虑过的替代方案**: 将总大小超限也纳入 continue-on-error（即尽量上传能上传的部分，忽略超出 300 MB 之后的文件）——与规格 Edge Case 中"系统必须在提交前阻止操作，并明确提示批次总大小超限"的整体阻止型语义相冲突，故不采用。

## 决策 4：API 端点的复用方式

- **决策**: 复用现有路由 `POST /{lang}/console/upload`（`src/app/[lang]/console/upload/route.ts`），不新增独立的批量上传路由；仅调整其请求解析（读取多个 `file` 字段）与响应体（返回逐文件结果数组）。
- **理由**: 现有路由已经封装了鉴权（`getCurrentUser`）、父目录校验、`getDb()` / `getStorage()` 环境切换等逻辑，可直接复用；符合仓库"精准手术式修改"的约定，避免维护两套相似的上传逻辑。
- **考虑过的替代方案**: 新增 `POST /{lang}/console/upload/batch` 等独立路由——会造成鉴权与父目录校验逻辑重复，且客户端需要区分调用哪个端点，徒增复杂度，故不采用。

## 决策 5：客户端前置校验与服务端权威校验的关系

- **决策**: `FileUploadForm` 的 `<input type="file">` 增加 `multiple` 属性；提交前在客户端同步校验文件数量（≤20）与总大小（≤300 MB），超限时立即阻止提交并提示，不发起网络请求；单文件大小（≤20 MB）同样做客户端预检查以尽早提示。所有限制在服务端重新校验，客户端校验仅用于提升体验，不作为唯一防线。
- **理由**: 满足 SC-003（"能够在提交前立即…得到明确的超限提示"）的用户体验要求，同时遵循"不可信任客户端输入"的安全基线，服务端必须独立、权威地重新校验全部限制。

## 结论

上述决策均基于现有代码结构与依赖，无需引入新的第三方库、数据库迁移或基础设施变更；所有 NEEDS CLARIFICATION 项已在规格阶段（`spec.md` 的 Clarifications 小节）解决，Phase 0 无遗留未决问题。
